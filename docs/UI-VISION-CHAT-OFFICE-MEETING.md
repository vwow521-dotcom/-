# AI Bridge UI 愿景：Chat / Office / Meeting

> 记录日期：2026-11-19  
> 状态：产品与交互设计备忘录，**不是已经实现的功能说明**  
> 讨论背景：现有会议室面板功能完整，但聊天、会议、交接、审批、Agent 状态集中在一个“三栏仪表盘”中，重要信息相互争夺注意力。下一步优先解决信息架构，而非单纯换配色、增加装饰。

## 1. 一句话定位

**在本地 Web 界面管理一支由不同厂商原生桌面端 AI 组成的团队。**

用户是老板：提出目标、召集讨论、审批、打回、查看结果；AI 是员工：在各自熟悉的原生桌面产品中自主决定实现办法。AI Bridge 充当共同的办公室和协作层，而不是重造一个 CLI、IDE 或模型 Harness。

核心体验由三个视图构成：

| 视图 | 灵感 | 主要回答的问题 | 应当突出的动作 |
| --- | --- | --- | --- |
| **Chat（聊天室）** | Discord 群聊 | 大家在说什么？我要找谁？ | 发消息、@一人、@多人、回复 |
| **Office（办公室）** | 腾讯 Marvis 的办公室动效概念 | 员工现在在做什么？有没有异常？ | 观察、选中员工、跳到任务/会话 |
| **Meeting（会议室）** | offAice 的圆桌协作 | 要做什么、由谁做、如何验收？ | 提案、互评、定稿、批准、驳回 |

三者不是三个后端系统，也不是复制三份状态：**共享同一套任务、会议、信箱、Agent 状态与审批事实，只是不同的阅读和操作入口。**

## 2. 已有底座：不要推倒重来

截至 2026-11-19，仓库已具备以下经过开发测试的能力（仍有稳定性问题待完善）：

- Web 发布目标，一名 Agent 编码，另一名审查；支持审批与返工；
- 圆桌会议：提案、互评、定稿，能够跨多个回合批准或打回；
- 聊天：用户对单个或多个 Agent 发消息，Agent 之间可以互相 @；
- 邮递员与信箱：消息持久化、回执、任务交接；通过原生桌面端适配方式唤醒 Claude 和 Codex，避免模型层不停轮询；
- 任务 DAG、文件租约、Git 提交与可查看的 Agent 状态；
- 现有页面：`panel/room.html`、`panel/room.css`、`panel/room.js`；状态读取与事件更新已存在。

**本轮只规划 UI/UX 演进，不修改任务状态机、MCP 协议、门铃、数据库或原生桌面端集成。**

可以对照 `docs/ARCHITECTURE-v2.md`、`docs/DESIGN.md` 和 `docs/USAGE.md` 了解实现边界。历史草案中若残留早期轮询方案，以最新实现为准。

## 3. 体验原则：从“飞机仪表盘”变成“办公室”

1. **优先显示需要人决策的事。** 待审批、待回答、投递异常必须醒目；门铃类型、会话绑定、文件租约细节默认折叠。
2. **场景决定版式。** 聊天适合时间线；会议适合多方方案比较与决策；办公室适合状态总览。不要把所有数据都塞在同一条时间线。
3. **保留上下文。** 从 Office 选中 Codex，可以直接跳到它所在任务或会话；从 Chat 中的任务通知，可进入 Meeting/任务详情并返回原位置。
4. **重要操作不能被动画淹没。** 批准、驳回、停止任务的入口明确且有上下文；高风险操作有确认步骤。
5. **不假装有“活人”在工作。** 动画只表达系统已有证据支持的状态；不应因为 Agent 看似在线就播放“正在编码”。
6. **保留高级诊断入口。** 连接状态、消息回执、门铃降级、租约等仍然可查，但不占据日常主界面。
7. **原生桌面端做执行。** 控制台传递工作目标、边界、验收标准，不代替 Claude/Codex/其他原生 Harness 编排每条搜索、编辑和测试命令。

## 4. Chat：要有 Discord 式“同事感”

**定位：日常沟通的默认入口。** 继续沿用已经跑通的群聊模型，而不是重新设计聊天协议。

建议布局：
- 左侧：项目/频道或话题入口（初版可以只有“总群”），Agent 成员列表及简要状态。
- 中间：按时间排序的真实对话、@ 提及、引用回复、简短系统提示；输入框固定在底部。
- 右侧或抽屉：所选成员/话题的详细资料，按需打开，不常驻展示全部诊断字段。

行为：
- 支持用户 @单个、@多个 Agent，也支持 Agent @Agent；群发与点对点显示清晰的收件对象。
- “消息已写入”“已投递/已按门铃”“已读取”等回执要如实区分；回执细节可点开，不必每条都常驻满屏。
- 会议邀请、审批请求等可以作为**简短的可跳转事件卡片**出现在聊天中，完整处理流程仍在相应视图完成。
- 防止 Agent 互相 @ 无限对话：由现有调度/权限机制控制最大往返与停止条件；UI 显示会话是否仍在进行。

**不要做：** 将每轮会议的全文提案、文件变更清单和每张审批表直接展开塞进普通群聊。

## 5. Office：让系统状态变得直观

**定位：查看公司运转的状态视图，不是另一套复杂的任务看板。**

参考 Marvis 的“虚拟办公室”表达方式，但只借鉴交互概念，**不复制其角色素材、动画资源或视觉资产**。

状态与视觉动作映射（示例，最终以真实后端数据为准）：

| 可确认的状态/事件 | 办公室表现 | 点开后的信息 |
| --- | --- | --- |
| 在线且空闲 | 坐在工位、待命 | Agent、原生端、最近任务 |
| 领取并执行编码任务 | 工位工作动效 | 任务、负责人、进度、最近交接 |
| 审查中 | 查看文件/审阅动效 | 审查目标、结果与待办 |
| 会议轮次进行中 | 参会者出现在会议桌 | 跳转该会议轮次 |
| 待老板审批 | 审批桌收到文件，适度提醒 | 打开审批内容 |
| 网络异常/门铃失败 | 清晰的异常图标或静态状态 | 链接到诊断面板 |
| 状态未知 | 静态显示“状态待确认” | 最近一次可靠状态时间 |

动效原则：
- 第一版采用轻量 2D/CSS/SVG 动效即可，**不先做 3D 或复杂游戏引擎**。
- 有闲置/低性能模式，支持减少动态效果；手机端优先不卡顿、可操作。
- 角色可有小动作和轻松氛围，但不能让动画掩盖真实进度和异常。
- Office 中只保留少量常用操作：“看任务”“发消息”“查看会议”“查看异常”；复杂配置放到侧栏/设置。

## 6. Meeting：会议决定任务，执行交给原生 Harness

**定位：做决策与任务分工，不手把手教 AI 怎么写代码。**

推荐流程：

```text
老板提出议题
  → 邀请参会 AI
  → 第一轮独立提案
  → 一轮或多轮互评 / 质疑
  → 主持人归纳分歧与共识
  → 形成结构化任务清单
  → 老板批准 / 打回 / 追加约束
  → 邮递员投递给对应 AI
  → 原生桌面端自主执行
  → 交接、审查、必要时再次审批
```

### 会议产出不应只是一大段聊天记录

建议形成可复核的任务卡（具体字段可映射现有任务模型）：

- **What**：目标、交付物；
- **Who**：负责人、审查者、参会者；
- **Done**：可验证的验收标准；
- **Scope / Constraints**：允许触及的文件范围、依赖、禁止事项；
- **Why**：关键设计依据、保留的异议；
- **When / Dependency**：依赖完成后才能开工、需要人工审批的节点。

**How 留给 Agent 自己的原生桌面端。** 会议可以讨论技术路线，但不应强制控制台重写一套模型内部的搜索、编码、终端调用和测试策略。自主性不等于越权：文件租约、任务取消、人工审批和权限边界仍由协作桥执行。

### 会议 UI

- 顶部：议题、当前轮次、参会成员、流程阶段。
- 中部：提案比较和争议点，而非只有长篇时间线。
- 底部/侧抽屉：当前决策入口——“继续互评”“请求定稿”“批准分派”“打回修改”，每次只突出当前合法动作。
- 历史回合、全文、引用证据、会议纪要按需展开。
- 明确显示“等待哪位 AI 发言”“哪些提案尚未完成”，并允许老板处理未响应成员。

## 7. 跨视图统一的“待你处理”

无论处于 Chat、Office 还是 Meeting，都应有一个紧凑、易找到的待办入口：

- 等你批准的会议定稿；
- 等你批准/打回的代码交接；
- Agent 向你提出的问题；
- 需要人工干预的连接/投递异常。

入口显示数量与最紧急事项。点击后打开对应的**上下文审批卡**，而不是让用户在历史消息里翻找按钮。

建议待办为跨视图抽屉或浮层，**不再发展成第四套臃肿主页面**。审批动作仍调用现有 API，必须保留失败反馈、权限约束与确认步骤。

## 8. 桌面、手机、局域网

- 桌面：Chat 侧栏可以常驻；Office 可看完整房间；Meeting 利用较宽区域做提案对比。
- 手机：优先“当前待办 → 当前内容 → 发消息/决定”；侧栏变抽屉，办公室改紧凑示意，审批按钮无需滚动很远才能找到。
- 离开电脑桌仍可查看进度和审批，是重要使用场景；但 **127.0.0.1 只对本机有效**，以后如开放局域网访问，必须有身份验证、访问控制，不能直接将可执行任务的接口裸露给整个网络。

## 10. 明天动手的最小计划

先不动后端，也不必一次画完三个视图：

1. **画出页面骨架**：全局导航 + 内容区 + 常驻待办入口。
2. **先改 Chat**：直接复用当前群聊行为，把会议/交接的大卡片从普通聊天阅读流中抽出来，留下跳转摘要。
3. **再改 Meeting**：优先修复“从看见待审批到真正审批”这条最关键的操作路径。
4. **最后试 Office 原型**：先让 Claude/Codex 的少数真实状态映射到工位，不急着制作美术资产。

### 完成标准（这一阶段）

- 老板打开页面，短时间内能判断：**有什么需要我处理、谁在工作、我怎样给他们下达新目标**。
- 用户发消息、@AI、审批会议、打回交接的行为与旧页面保持一致。
- 三个视图使用同一份后端状态；切换视图不重复触发任务，也不丢失输入草稿。
- 在小屏幕上不用穿越整张“仪表盘”寻找审批按钮。
- Office 的每个状态说明都能对应真实来源，不虚构模型活动。

## 11. 暂时不做

- 重做 Claude/Codex 自身的代码编辑器或工具执行流程；
- 为了改 UI 直接重写后端、MCP、邮递员或数据模型；
- 大量 3D 动画、复杂角色养成或游戏机制；
- 复制 Discord、Marvis 的品牌素材和受版权保护的视觉资产；
- 只为展示炫酷效果而引入不可靠的“假实时”状态。

---

**设计准则总结：Chat 像同事聊天；Office 像走进办公室；Meeting 像真正开会；原生桌面端继续负责真正干活。**
