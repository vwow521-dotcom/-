# M0 原型实测指南

目的：用真实的 Claude 桌面版（Code 标签页）和 ChatGPT 桌面版里的 Codex，验证 [DESIGN.md](DESIGN.md) 第 5 节的三个风险。脚本冒烟测试（`npm run m0:smoke`）已通过，下面是只能由你在图形界面里完成的部分。

## 0. 启动桥

```powershell
cd E:\Interaction-ai
npm run m0
```

保持这个窗口开着。面板：<http://127.0.0.1:7878/>（每 3 秒自动刷新）。所有事件记录在 `.bridge/m0-log.jsonl`。

可调环境变量：`BRIDGE_POLL_SECONDS`（单次等待阻塞秒数，默认 50）、`BRIDGE_OFFLINE_SECONDS`（失联判定，默认 180）、`BRIDGE_PORT`（默认 7878）。

## 1. 接入 Claude（风险 3）

本仓库根目录已有 `.mcp.json`，指向 `http://127.0.0.1:7878/mcp`。在 Claude 桌面版的 Code 标签页里，以 `E:\Interaction-ai` 为目录新开一个会话，按提示允许名为 `bridge` 的 MCP 服务器。

要在其他项目目录里用，就把同样的 `.mcp.json` 复制到那个项目的根目录。

## 2. 接入 Codex（风险 3）

在 `~/.codex/config.toml`（即 `C:\Users\<你>\.codex\config.toml`）末尾加上：

```toml
[mcp_servers.bridge]
url = "http://127.0.0.1:7878/mcp"
tool_timeout_sec = 120
```

然后重启 ChatGPT 应用，在 Codex 里选一个项目新开对话。

需要确认的点：
- ChatGPT 应用里的 Codex 是否读取这份 `config.toml`。
- 是否支持 `url` 这种 HTTP 类型的 MCP 配置。
- 桥的面板或日志里是否出现 `mcp_session_open`。

如果连不上，把报错发给我。备选方案是做一个 stdio 转接程序（设计文档里提到过）。

## 3. 启动提示词

**在 Claude 会话里粘贴：**

> 你是 AI 协作桥中的 `claude`，负责规划和审查。先调用 bridge 的 `join`（agent_id = "claude"），然后严格按它返回的 protocol 循环：调用 `wait_for_my_turn`；返回 keep_waiting 就立刻再调用，不要停下、不要向我汇报；返回 your_turn 就完成工作并调用 `submit_handoff`，然后回到等待循环。等待被中断或取消时，也立刻重新调用 `wait_for_my_turn`。

Claude 的 bridge 已加到全局配置 `~/.claude.json`（备份在同目录的 `.claude.json.bak-bridge-*`），任何项目新开的会话都能用。

**在 Codex 会话里粘贴：** 同上，把 `claude` 换成 `codex`，"规划和审查"换成"编码"。

### 发现的问题（需在 M0.1 修复）

1. **同名身份冲突**：Codex 会话误用了 claude 的启动提示词，以 `claude` 身份 join，和真正的 Claude 抢接力棒。两个同名会话轮流调用 wait，还会把对方阻塞中的那次调用挤掉，导致 4.5 分钟内出现 44 次短间隔的 wait 调用。修复思路：一个 agent_id 只绑定一个在线会话，join、wait、submit 都校验会话。
2. **没有"目标完成"状态**：审查通过后，Codex 又回了一个确认式交接，接力棒回到 Claude，靠 Claude 自己判断才停下。修复思路：`submit_handoff` 加上 `goal_done`，目标完成后桥收回接力棒、结束本次运行。
3. **运行中可以重复点"开始"**：13:29:29 第二次点开始，重置了正在工作的持有者。修复思路：有运行在进行时拒绝启动，要求先点停止。
4. 另外：13:37 有 `copilot-cli` 连上了桥（它也读到了 bridge 配置），属于正常现象。根目录的 `npm run typecheck` 不检查 `playground/`。

### M0.1 修复（已完成，冒烟测试 22 项全过）

1. **身份绑定**：每个 agent_id 只绑定一个 MCP 会话。原会话还在线时，其他会话 `join` 同名身份会被拒绝，并提示"你可能拿错了启动提示词"。确实要替换时用 `join(agent_id, takeover=true)`，原会话随后的调用都会被拒。`wait` 和 `submit` 也会校验会话。会话关闭（HTTP DELETE）会立即释放身份。客户端直接消失时，身份要等 `BRIDGE_OFFLINE_SECONDS` 内都没有活动后才能被新会话正常 join。
2. **目标完成**：`submit_handoff` 新增 `goal_done`。设为 true 后，桥结束本次任务，不再交接给任何人；所有 agent 回到空等。your_turn 的说明里也提示 AI：目标完成时用它，不要再发"确认收到"式的交接。
3. **重复开始**：有任务在进行时，面板或 API 的"开始"会返回 409，要先点停止。

结论：**风险 2 通过**。两边都能连续空等 30 分钟以上，没有自行停下、没有向用户汇报。断网期间 Claude 中断了约 5 分钟，网络恢复后自己接上了循环，不需要人工介入。

空等成本（30 分钟以上，含启动提示词和工具定义）：Claude 上下文 8%，额度用量很低；Codex 上下文 6%，额度 1%。按这个速度，挂几个小时也只占小部分上下文，成本可以接受。如果要进一步降低，可以把 `BRIDGE_POLL_SECONDS` 调到 100 左右，前提是两边的工具超时都调到 120 秒以上，这样循环次数大约减半。

设计启发：网络波动和会话真的失联，在"距上次调用"这个指标上看起来一样。失联判定应该先显示"可能断网"，宽限一段时间后再触发兜底 B。
