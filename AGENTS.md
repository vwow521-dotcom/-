# AGENTS.md

This file provides guidance to Codex when working with code in this repository. It mirrors CLAUDE.md; keep the two in sync.

## What this is

A local "AI collaboration bridge". One long-running Node daemon exposes an MCP server over Streamable HTTP, plus a web panel. AI agents in different desktop products (Claude desktop's Code tab, and Codex inside the ChatGPT Windows app; later Gemini, Antigravity and DeepSeek) use it to hand work to each other through a role pipeline that has human approval gates. Work travels as **mail**, and a **postman** wakes idle agents with product-specific **doorbells** instead of having them poll.

The design docs are in Chinese. `docs/ARCHITECTURE-v2.md` is the current architecture: the postman, the borrowed designs, and the S1/S2 spike results. `docs/DESIGN.md` covers the original goals and decisions. Read them before changing behaviour. The user communicates in Chinese, and the agent-facing tool text and the panel are in Chinese too. How to use the bridge: `docs/USAGE.md`.

Stage: M2b (postman), M2b.1 and M2c (meetings, task DAG, file leases, scoped commits) and doorbell drivers with the Codex queue doorbell (0.5) are done, and the bridge ships as an installable package (0.5, `ai-bridge` CLI). Next is M2d: the panel from the roundtable/board prototype. After that comes M3: ACP background workers and clipboard members (Gemini, DeepSeek). Treat `src/m0/` and `spikes/` as records. Don't extend them.

## Commands

```
npm start -- --project <dir> [--port 7878]   # dev: run the daemon from src via tsx (MCP /mcp, panel /, JSON API /api/*)
npm run smoke       # end-to-end regression: own daemon on port 7891, temp git repo, fake Claude pipe, fake Codex transcripts
npm run typecheck
npm run build       # tsc -p tsconfig.build.json → dist/ (src/m0 excluded)
npm run reinstall   # npm pack into release/ → npm i -g → ai-bridge setup --refresh → ai-bridge doctor (local tree)
ai-bridge update    # fetch GitHub main into a temp dir → npm ci → npm pack → npm i -g → setup --refresh → doctor (never `npm i -g github:…`: npm runs the clone's install in global mode, prepare fails, and the old install is already gone)
npm run cli -- <cmd> [--dry-run]   # run the CLI from this tree (setup/uninstall/init/start/doctor)
```

**The user's Claude and Codex point at the globally installed copy** (`%APPDATA%\npm\node_modules\ai-bridge`), not at this tree. After changing `bin/` or `src/`, run `npm run reinstall` so the clients pick it up; once pushed, `ai-bridge update` installs from GitHub. `prepare` builds and writes `dist/build-info.json` (commit), which `doctor` compares with GitHub main. `setup --refresh` (used by both) only touches bridge entries that already exist: the user removed Codex's bridge entry on purpose, so never re-add a client they removed. `npm run cli -- setup` would point the clients at this dev tree instead. Testing `setup`/`uninstall` against copied config files is not isolated: they also clean `.codex/hooks.json` in the real project folders listed in the config. Use `--dry-run`.

Extend `scripts/smoke.ts` whenever you change engine, proxy or hook behaviour.

## Architecture

- **Mail is the only way work reaches an agent.** `Engine.sendMail` → `mail` table (one row per recipient, `id` primary key = dedupe) → `kick(agent)` wakes a `wait_for_mail` poller and/or rings an open doorbell. Status flow: `queued → rung → fetched → acked`, plus `stuck` (gave up after `mail.max_rings`; the human is told to wake the agent) and `void` (a task that was stopped or replaced). `sweep()` runs every 5 s, re-rings mail that is rung but not fetched, and flags overdue acks.
- **Runs, tasks, attempts:** a run is one goal made of **tasks** (a DAG: `depends_on`, `paths`; `tasks` table, status `pending → active → done|cancelled`). Each task runs its own stage chain stored on the task row: a pipeline run ("开始") is one task `T1` whose stages are `pipeline`; a meeting-planned task uses `task_template` with `owner`/`reviewer` filled in (reviewer stages are dropped when a task has none). `schedule(run)` starts every pending task whose dependencies are done and whose `paths` don't collide with someone else's lease, and finishes the run when no task is left. Each stage handed to an agent is an **attempt** (`ready → in_progress → (awaiting_approval → approved|rejected) | done`). An agent works on one task at a time: `deliver(agent)` mails its oldest ready attempt only when it has nothing in progress. `fetch_inbox` turns a task mail into the turn payload and moves the attempt to `in_progress`. `submit_handoff` commits, acks the task mail and advances that task. The run is `awaiting_approval` only while every live attempt waits at a gate. A rejection creates a new attempt of `on_reject` with structured `feedback` (`Feedback` in store.ts: user_requirements / blocking / observations); when that rework attempt finishes, its feedback is carried (`kind: "carried"`) into the next stage. Reviews with no file changes still commit (`--allow-empty`, `git.commit_reviews`). `ask_human` doesn't block; the answer arrives as an `answer` mail. Only one open run or meeting exists at a time. Pre-M2c databases get one `T1` task per run on startup (`migrateLegacyRuns`).
- **Meetings** (`meetings`, `meeting_turns`): round 1 is proposals from every participant, then the human opens more critique rounds or asks the facilitator for the final plan (`meetingNext`; allowed before everyone has spoken, the rest of that round's mail is voided). Every round is a `meeting` mail with id `meeting-<id>-<round>-<agent>`; `fetch_inbox` builds the payload (all earlier rounds + the human's note) at fetch time and voids mail for a round that is over. `submit_meeting_turn` acks it; the final turn must carry a valid task list (`validatePlan`: ids, owners, dependencies, cycles). Approving writes the minutes to `meetings.dir` (default `doc/meetings/<date>-<topic>.md`), commits only that file, and creates the run with its tasks.
- **File leases** (`leases` table): an active task holds an exclusive lease on each of its `paths` (no expiry, released when the task ends or the run stops). Agents add more with `reserve_paths` (TTL, renewed by calling again; expired leases stop counting and show yellow) and drop them with `release_paths`. A conflicting request is refused, returns the holder, and mails the holder. `globsOverlap` is exact for literal paths and conservative (literal-prefix check) when both sides have wildcards; a trailing `/` means the whole directory.
- **Doorbells** (`src/doorbells/`): the only code that knows how a product is woken. The engine never branches on a product; it asks the `Doorbells` registry. Each agent has an ordered **chain** (config `agents.<id>.doorbell`: a list, a single kind, or `auto` = `PRODUCT_DOORBELLS[product]`: `codex` → `codex-queue, codex-hook, poll`; `claude-code` → `claude-socket, poll`; unknown product → whatever registers). `poll` always ends a chain. `kick(agent)` wakes a blocked `wait_for_mail`, then rings the first doorbell that is `available()` now. A failed ring (`ringFailed`) requeues the mail and falls through to the next one. After a successful ring of a `verify` doorbell, `checkWake` waits `BRIDGE_WAKE_GRACE_SECONDS` (default 30): any tool call from the agent, or the agent already working on a bridge task, counts as awake. Otherwise it tries the next doorbell, and when none is left, `alertUnanswered` shows "叫不醒" on the panel and sends a toast. `join`'s waiting instructions come from the chain's first `possible()` doorbell. Adding a product = a driver (and later a product profile), not engine edits.
  - `claude-socket` (`parked.ts`): `bin/bridge-mcp.mjs`, the stdio MCP proxy, forwards every call to the daemon and sends MCP `DELETE` on stdin EOF to release its session's bindings. In Claude it injects `_doorbell: "claude-socket"` into `join`, long-polls `GET /api/doorbell/wait`, and writes `{"type":"auth"}` + `{"type":"user"}` NDJSON frames to the undocumented `CLAUDE_CODE_MESSAGING_SOCKET` Windows named pipe when rung. Failures are reported to `/api/doorbell/result`.
  - `codex-queue` (`codex-queue.ts`): the bridge runs `codex queue --thread <id> --message <wake text>`. The Codex desktop app drains `~/.codex/queue_1.sqlite` itself: an idle conversation starts a real new turn in ~6 s (`turn_trigger: "queue"`), a busy one picks it up when its turn ends. The CLI is `BRIDGE_CODEX_BIN` (a `.js/.mjs` runs under node), else the newest `~/.codex/packages/app-server-daemon/releases/*/bin/codex.exe`, else `codex.exe` on PATH. It skips queuing when Codex's queue already holds an item for the thread. A failure takes it out of the chain for 10 minutes. The thread id is the agent's `codex-thread` endpoint; it is ignored when the agent joined from a newer MCP session than the registration (a new conversation that hasn't ended a turn yet).
  - `codex-hook` (`parked.ts`, `bin/codex-stop-hook.mjs`): the Codex Stop hook. Threads without a completed `bridge.join` `McpToolCall` in the transcript get `{}` at once. A joined thread registers its `session_id` (`POST /api/agents/:id/endpoint`, kind `codex-thread`; the old `/api/codex/thread` still works). The answer `park:false` (codex-queue can reach the agent) makes it return `{}` so the turn ends; otherwise it parks on `/api/doorbell/wait` and answers a ring with `{"decision":"block","reason":…}`. Codex drops many of those blocks (§14 of the architecture doc), which is why codex-queue comes first. It logs stdin, parking time, mail IDs and stdout to `<tmp>/ai-bridge/codex-stop-hook.jsonl`, heartbeats after a quiet park window, and rides out a bridge restart for `BRIDGE_DOWN_GRACE_SECONDS` (default 90). While it is parked, Codex holds the user's typing and queued messages until the hook returns.
  - The desktop app's app-server control socket can't wake a desktop thread: it belongs to a separate managed App Server and answers `thread not found` (tested 2026-11-19).
- **Durable vs in-memory:** runs, tasks, attempts, handoffs, leases, meetings, mail, notes, questions, events and agent endpoints (`agent_endpoints`, e.g. Codex conversation ids) are in `<project>/.bridge/bridge.db` (`store.ts`, `node:sqlite`). Presence, identity bindings, parked doorbell waiters, wake alerts and blocked waits are in memory. After a restart agents re-`join`, and `resendLiveTask` re-mails a live task.
- **Identity binding:** each agent_id is bound to one MCP session (`bindingError`). A second session can only take it with `join(takeover=true)`, or after the human presses 释放 on the panel (`release`) or the agent calls `leave`. The proxy replays join with `takeover` after the daemon restarts.
- `daemon.ts`: HTTP, MCP transports, the JSON API and SSE `/api/stream` (a "change" ping). The panel (`panel.ts`) re-fetches `/api/state` and rebuilds only when the JSON differs. `notify.ts` shows Windows toasts through PowerShell/WinRT; `BRIDGE_NOTIFY=0` disables them.
- `git.ts`: a task with `paths` or leases, or with other active tasks, commits declared changes and changes in its own scope, excluding other tasks' leases. Reviews commit only declared changes and can record a verdict via an empty commit (`git.commit_reviews`). Scoped submissions use `commitPaths` (`git add -A -- <pathspecs>` + `git commit --only`, pathspecs `:(top,literal)…`). A lone non-review task without paths or leases retains `commitAll`. `changedFiles` is compared with `files_changed`, the task's `paths` and other stages' `owns`; mismatches and files left uncommitted become `scope_notes` (shown on the approval card, not blocking). `.bridge/` writes its own `.gitignore`.
- `cli.ts` → `ai-bridge` (`bin/ai-bridge.mjs` imports `dist/cli.js`): `setup` writes `~/.claude.json` `mcpServers.bridge` and `~/.codex/config.toml` `[mcp_servers.bridge]` (both: absolute node + installed `bin/bridge-mcp.mjs`), and a **user-level** `~/.codex/hooks.json` Stop hook. It also removes legacy project-level copies for every `[projects.'…']` in Codex's config. It only replaces entries it recognises as the bridge's and backs up every file first. `uninstall` reverses all of it. `doctor` checks paths, hook trust (`[hooks.state.'<hooks.json>:stop:…']`), legacy hooks, proxy and daemon.
- `config.ts`: `<project>/bridge.config.yaml`, validated with zod (`pipeline`, `task_template`, `meetings`, `leases`, …). `DEFAULT_CONFIG_YAML` must stay in sync with `bridge.config.example.yaml`.
- `AGENTS.md` mirrors this file for Codex; update both together.
