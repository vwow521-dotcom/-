## claude 的提案

五项分成三个任务：

### ① 取消宽限
**现状**：`acp.ts` 里 `cancelGraceMs = 3000`，超时就调 `fail()`。这会计一次失败、结束进程、进入退避。Antigravity 一个回合常常 40 秒以上，3 秒内收不到 `stopReason: cancelled` 很正常。

**改法**：
- 宽限默认改成 30 秒，可以用 `BRIDGE_ACP_CANCEL_GRACE_SECONDS` 覆盖，写法和现有的 `BRIDGE_ACP_RETRY_SECONDS` 一样。不加配置项，避免和 ⑤ 都去改 `config.ts`。
- 超时后不再算失败：
  - 记一条事件 `acp_cancel_timeout`；
  - 结束进程树，但 `failures` 不加一，也不进入退避；
  - 下次有信时照常懒启动，并 resume 原来的会话。
- **理由**：代理不理会取消，不说明它坏了；按崩溃处理会让一次停止 run 就吃掉 30 秒以上的退避。

### ② 孤儿进程
Windows 上 Node 没法不借助原生模块就用 job object，所以方案是**看门程序**加**启动清理**两层。

**看门程序**（主要手段）：新建 `bin/acp-guard.mjs`。
- 桥不再直接拉起代理，而是运行 `node acp-guard.mjs <daemonPid> -- <command> <args>`。
- 看门程序用 stdio pipe 透传 JSON-RPC，每 2 秒用 `process.kill(daemonPid, 0)` 检查守护进程是否还在。
- 守护进程不在了，或自己的 stdin 收到 EOF，就对代理执行 `taskkill /T /F`，然后自己退出。
- 这样守护进程崩溃或被 `/F` 结束时，几秒内就能清理干净，不依赖下次启动。

**启动清理**（兜底）：
- spawn 后把代理的 PID 和进程创建时间写进 `agent_endpoints`（kind 为 `acp-pid`）。
- 下次启动时，只有 PID 和创建时间都对得上才结束它，防止 PID 被系统复用后误杀别的进程。
- 用 PowerShell 的 `Get-Process` 取创建时间。

**风险**：
- 多一层进程，stdin/stdout 透传要处理背压和 EOF；
- `doctor --probe` 也应该走看门程序，保证超时退出时同样不留进程。

### ④ 退避档位
需求文档写的是「30 秒、2 分钟、10 分钟，连续 3 次失败后停止」，实现只有前两档，第 3 次失败就停。我建议实现改成和需求一致：
- 第 1 次失败等 30 秒，第 2 次等 2 分钟，第 3 次等 10 分钟；
- 第 4 次失败才停止，等手动重启。
- 架构文档第 23 节同步改写。
- **理由**：需求是用户定的约束，实现应该向需求靠拢，而不是反过来改需求。

### ③ permissions: allow 的风险提醒
在 USAGE 第 9 节加一段：
- `allow` 会自动批准代理在项目目录里执行的**任意 shell 命令**，包括写文件、git 操作和网络请求。实测 Antigravity 在 accept-edits 模式下仍会为 `Get-Content`、`git diff` 请求权限，桥会一律放行。
- 建议只在可信的项目里用 `allow`。不确定时用 `deny`，并在成员详情的「最近权限决定」里查看被拒绝了什么。

### ⑤ agents.<id>.notes
- **配置**：在 `config.ts` 的 agent schema 里加 `notes: z.string().trim().max(200).optional()`，同步更新 `DEFAULT_CONFIG_YAML` 和 `bridge.config.example.yaml`。本仓库的 `bridge.config.yaml` 给 antigravity 和 deepseek 写上「轻活：文档、文案、纪要、第二意见；额度有限」。

- **范围**：panel 和 join 先不改，范围最小。
- **验收**：smoke 里有一条用例，确认定稿轮的会议信带有 notes，互评轮的信不带。

## 一、方案思路与关键决策

### 议题 ①：ACP 取消宽限过短（Antigravity 回合较长）
- **现状分析**：`src/doorbells/acp.ts` 中硬编码了 `cancelGraceMs = 3000`（3 秒）。当回合被取消（例如任务作废或停止运行）时，桥向 ACP 发送 `session/cancel`。但 Antigravity 等 Agent 在处理包含复杂工具调用（如长时间命令执行、代码生成、模型流式思考）的回合时，3 秒极易超时，导致定时器直接调用 `this.fail(new Error("ACP 代理没有确认取消回合"))`，把正常的取消误判为代理崩溃并进入故障退避。
- **改进方案**：
  1. 将默认取消宽限时间从 3 秒延长至 **15 秒**（`cancelGraceMs = 15000`），给 Agent 足够时间优雅中断工具调用并返回取消后的 `session/prompt` 响应。
  2. 支持通过环境变量 `BRIDGE_ACP_CANCEL_GRACE_SECONDS`（默认 15）动态覆盖，便于测试环境缩短或特定高延时模型环境放宽。
- **决策理由**：15 秒是业内兼顾交互等待与子进程优雅清理的标准窗口，既防止误报崩溃，又不会导致队列长时间卡死。

### 议题 ②：守护进程被强制结束时 ACP 子进程变孤儿
- **现状分析**：当前 `AcpRpc` 仅在正常退出调用 `terminate()` 时执行 `taskkill /PID <pid> /T /F`。但当桥守护进程遭遇异常退出、强制结束（Task Manager / SIGKILL）或终端关闭时，Node 进程被直接杀掉，而 Windows 下通过 `spawn` 派生的子进程（如 `agy.exe`、`DeepSeek Harness.exe`）不受父进程消亡影响，会变成孤儿进程长期滞留后台并占用资源。
- **方案对比与决策**：
  - **Job Object 方案**：Windows 原生 Job Object 虽然支持 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`，但 Node.js 标准库未内置此能力，引入外部 C++ 原生扩展（node-gyp / native addons）会严重破坏项目的无编译便携性与跨平台构建体验。
  - **持久化 PID + 启动自愈清理方案（推荐采纳）**：
    1. 在 `AcpHost` 派生子进程时，将活跃子进程 PID 持久化记录（可存入 `store` 中的 `agent_endpoints` 表，kind 设为 `acp-pid`）。
    2. 在守护进程启动或 `AcpHost` 初始化时，主动检索上一次记录的 PID；若进程仍存在且经属性校验（匹配命令特征，防止 Windows PID 复用误杀），则调用 `taskkill /PID <pid> /T /F`（POSIX 下使用 `process.kill`）将其作为孤儿进程清理。
    3. 在 `daemon.ts` 的 `SIGINT`、`SIGTERM`、`beforeExit` 钩子中强化对 `doorbells.acp.shutdown()` 的调用。
- **决策理由**：纯 Node.js 实现，零 native 依赖，且能跨会话自愈，鲁棒性最强。

### 议题 ③：USAGE 提醒 permissions: allow 的风险
- **现状分析**：`docs/USAGE.md` 仅说明了 `permissions: allow` 会优先选「允许一次」或「始终允许」，缺乏足够的安全警示。在 `bridge.config.yaml` 中配置为 `allow` 后，桥会自动放行 ACP Agent 发出的所有工具调用（包括任意系统命令执行、磁盘任意文件修改与删除）。
- **改进方案**：
  - 在 `docs/USAGE.md` 的「9. 后台成员」章节增加明确的 **【高危/安全警示】**：
    1. 警示 `permissions: allow` 相当于授予 Agent 完全的宿主系统执行权限与信任。
    2. 提醒用户若模型出现幻觉或提示词注入风险，可能执行非预期的破坏性指令（如误删文件、修改非工作目录文件等）。
    3. 建议仅在受信任的代码库和明确受控的开发任务中开启；敏感环境推荐使用默认的 `permissions: deny` 或配合沙箱使用。
- **决策理由**：后台 Agent 缺乏人工实时看守，安全边界必须向用户明示。

### 议题 ④：退避档位的规范与实现统一
- **现状分析**：
  - `M3-ACP-MEMBERS.md` 描述为“按 30 秒、2 分钟、10 分钟退避后重试”；
  - `ARCHITECTURE-v2.md` 描述为“两次自动重试分别等待 30 秒和 2 分钟。第三次失败后等待手动重启，门铃链降级仍使用全局的 `doorbells.cooldown_seconds`（默认 10 分钟）”；
  - `src/doorbells/acp.ts` 实现为：第 1 次 30s，第 2 次 120s，第 3 次停止并标记 `stopped`；且代码中存在 `Math.min(retrySeconds, 30)` 导致无法通过环境变量调大退避秒数。
- **改进方案**：
  1. **规范对齐**：明确统一为“2 次自动指数退避重试（30s、120s）+ 第 3 次永久停止等待手动重启 + 门铃全局降级 10 分钟”。
  2. **实现修正**：移除 `Math.min(retrySeconds, 30)` 的硬性限制，允许自定义环境变量；规范常量定义。
  3. **文档同步**：同步更新 `docs/ARCHITECTURE-v2.md`，消除不同文档之间的理解偏差。

### 议题 ⑤：agents.<id>.notes 字段，推进人分配任务时可见
- **现状分析**：当前 `ConfigSchema.agents` 未定义备注字段；推进人（facilitator）在会议定稿生成任务时，只能看到成员 ID，无法直观了解成员画像（如“antigravity: 后台成员，新成员只接轻活”）。
- **改进方案**：
  1. 在 `src/config.ts` 的 `ConfigSchema.agents` 中增加可选字段 `notes: z.string().optional()`，并在 `bridge.config.example.yaml` 给出示例。
  2. 在 `src/engine/meetings.ts` 的 `meetingPayload` 中，将成员及其 notes 组合展示在 `taskSpec` 与成员列表中（例如 `owner（可选：codex、antigravity（新成员只接轻活）...）`）。
  3. 在 `src/engine/workspace.ts` 中将 `notes` 注入 agent 状态模型，使 Web 界面亦可展示。

1. **PID 复用误杀风险**：在自愈清理孤儿进程时，若 PID 被系统重新分配给其他无关程序，盲目 `taskkill` 会引发严重副作用。

# 提案：M3 收尾（deepseek）

我只读了代码和文档，没有改任何文件。结论：①④ 同源，都是 ACP 回合生命周期；②是进程生命周期；③是纯文档；⑤是配置加展示。建议 4 个任务：T1 先落配置与 ACP 取消/退避，T2 与 T3 在 T1 之后并行，T4 最后一次性收口文档。

## ① ACP 取消宽限过短：先别把取消超时当“失败”，再延长宽限

**现状与证据**
- `src/doorbells/acp.ts:13` 把 `cancelGraceMs` 写死为 3000；`cancel()` 发出 `session/cancel` 后 3 秒还没收到回合结束，就直接 `fail()`。
- `fail()`（`acp.ts:268-287`）会 `taskkill /T /F` 结束进程树、退回已取的信、`failures++`，并按 30 秒/2 分钟退避；连续 3 次失败后标记 `stopped`，只能人工重启。
- ACP 只有 `session/cancel` 通知，没有强制取消。Antigravity 实测回合 43 秒（`docs/ARCHITECTURE-v2.md` §23），长工具调用时 3 秒必然不够。于是“停止 run”“会议换轮/作废信”这类正常操作会杀进程并累计失败，甚至把成员停掉——这是最需要修的行为。

**决策**
- 宽限可配置：`agents.<id>.acp.cancel_grace_seconds` 默认 30，`cancel_max_seconds` 默认 120。
- 宽限内若仍收到该会话的 `session/update`（说明代理在收尾），按 10 秒步进续期到上限；完全静默就不续期。
- 取消超时与进程/协议失败分开记账：超时记 `acp_cancel_timeout`，结束进程树、退回未确认的信、立即重试，不进入退避、不累计 `failures`；连续 3 次取消超时才停止并说明原因。
- 理由：正常停止不应被当成代理崩溃；30 秒覆盖 Antigravity 的收尾，120 秒上限防止永久卡住。

**风险**：宽限期间新信不能并发 prompt，会被推迟；续期依赖 `session/update`，静默时代理仍要等满默认 30 秒。缓解：默认 30 秒而不是 120 秒，只有活动时才延长，事件里记录阶段与耗时，配置可调。

## ② 强杀守护进程后的孤儿 ACP 子进程

**现状**：`acp-rpc.ts` 直接 spawn 代理，`killTree()` 用 `taskkill /PID <代理> /T /F`，只有守护进程自己走到 stop/shutdown 时才执行（`daemon.ts:313`）。守护进程被 TerminateProcess、崩溃或被不带 `/T` 强杀时，`agy.exe acp ...` / DeepSeek 进程会留下，继续占 CPU、持有旧 MCP 会话；下次启动再起一个，形成重复进程和幽灵回合。

**决策：推荐纯 Node 监督进程，而不是 Job Object**
- Job Object（KILL_ON_JOB_CLOSE）最正统，但 Node 没有原生 API；要么加 native addon，要么用 PowerShell 创建作业并转发 stdio，复杂且难移植。
- 新增 `bin/acp-supervisor.mjs`：Windows 下 AcpRpc 不再直接 spawn 代理，而是 spawn 监督进程；监督进程透传真实代理的 stdin/stdout/stderr，并把自己的 stdin 当“生命线”。守护进程死亡 → 管道 EOF → 监督进程 `taskkill /T /F` 真实代理树后退出。POSIX 保留现有进程组逻辑，降低风险。
- 台账 `<project>/.bridge/acp-hosts.json` 记录监督进程 PID、真实代理 PID、启动时间、agent；daemon 启动最早期调用 `sweepAcpOrphans()`，只对“PID 存活 + 创建时间匹配 + 命令行含 `acp-supervisor.mjs`”的条目执行 `taskkill /T /F`，避免 PID 复用误杀；正常退出时删条目。
- 面板 PID 显示真实代理 PID，另附监督进程 PID；停止按钮仍结束整棵树；`doctor --probe` 仍只 initialize 并退出。

**风险**：多一层进程；强杀到清理完成有几秒窗口；监督进程自身被强杀时需要启动扫描兜底（台账覆盖）；可能影响现有 `doctor --probe` 的 PID 断言。测试：假代理跑长回合时从新增的 `/api/health` 取守护进程 PID 并 TerminateProcess，断言真实代理 PID 5 秒内消失；再伪造“监督进程被杀、代理存活 + 台账”，断言下次启动清理；正常 stop/shutdown 行为不变。

## ③ USAGE 提醒 `permissions: allow` 的风险

**现状**：`docs/USAGE.md` §9 只写“allow 优先选允许一次/始终允许”，没说这等于把后台代理每次工具调用（写文件、执行终端命令）自动放行，桥不审查内容、不限制目录。

**决策**：保留 `deny` 默认；在 §9 加显式风险段落：`allow` 只应在可信或可丢弃的项目里使用；需要逐步确认时用前台加入或 `deny`；说明 `allow_once` 缺失时回退 `allow_always`；权限决定可在成员详情审计。不改代码行为，只把已有语义写清楚。

## ④ 退避档位：规范与实现统一

**现状**
- `ARCHITECTURE-v2.md` §23：两次自动重试 30 秒、2 分钟，第三次失败停止；与代码一致。
- `docs/prompts/M3-ACP-MEMBERS.md:146`：“30 秒、2 分钟、10 分钟退避后重试；连续失败 3 次后停止”——三档退避加三次失败停止，实际会到第四次失败，自相矛盾。
- 代码：`BRIDGE_ACP_RETRY_SECONDS` 默认 30 且被静默 `min(..., 30)` 截断，档位 = base ×1、×4（`acp.ts:11-12, 275`）；`failures` 只在 `endTurn` 清零。

**决策**：以“30 秒、2 分钟两档，第三次失败停止”为准（恢复快，且与“三次后人工”一致），修正 M3 提示词这句话；档位改为 `agents.<id>.acp.retry_seconds` 配置，默认 `[30, 120]`，1–3 档、单档上限 1 小时；`failures > retry_seconds.length` 即停止，回合正常结束清零；`BRIDGE_ACP_RETRY_SECONDS` 只保留为测试覆盖（或删除并让 acp-smoke 改用配置），避免两个来源。顺带修掉取消超时也自增 `failures` 的问题（与 ① 同一处）。

**风险**：现有 acp-smoke 用 env 把退避缩到亚秒级，任务里要一起改；自定义该 env 的用户极少且 USAGE 未文档化。

## ⑤ `agents.<id>.notes`

**现状**：agents schema 只有 product/doorbell/acp，面板、会议 payload、`get_context` 都没有“这个成员适合接什么活”的位置。定稿人只能自己猜，容易把重活派给新成员。

**决策**：新增可选 `agents.<id>.notes`（字符串，trim，≤200 字），纯建议、不参与调度和 `validatePlan`：
- `/api/state` 的 `agents[].notes`，`get_context` 的 `members:[{id,product,notes}]`；
- 会议 payload 增加 `members`，taskSpec 加一句“分配前看 members.notes，注明只接轻活的成员不要派重编码/长测”；
- 面板：办公室成员详情、发起会议的成员列表、会议轮次参与者旁展示，空值不显示，HTML 转义；
- `bridge.config.example.yaml` 与 `DEFAULT_CONFIG_YAML` 注释同步（AGENTS.md 要求）。

**风险**：notes 会过期，所以只提示不强制；提醒不要把密钥写进 notes；长度上限防止面板被撑爆。

### 1. 议题 ①：ACP 取消宽限与超时处理
- **高度赞同 Claude 与 DeepSeek 的洞见（修正我方第 1 轮立场）**：

  - **原因**：当用户中止运行或会议作废信件时，后台代理正在执行耗时工具未能及时响应 `session/cancel` 属于正常业务流程中断，绝不等于代理本身损坏。如果超时直接调用 `fail()`，会强行给代理累加失败次数并打入 30s/2min 的退避冷却，导致后续新任务被严重阻塞，甚至 3 次后停机。

- **赞同 Codex 提出的“工作区租约与取消落定保护”**：
  - 当旧回合正在执行取消且尚未彻底退出时，应确保后续任务不会并发抢写同一工作范围，避免脏写冲突。

### 2. 议题 ②：Windows 孤儿进程治理
- **反对 Codex 提出的首选原生 Job Object 方案**：
  - 正如 Claude、DeepSeek 及我方第 1 轮所指出的，Node.js 官方在 Windows 上未内置 Job Object API。引入 C++ 原生 addon 或 node-gyp 依赖会彻底破坏协作桥“免编译、一键安装、纯 JS/TS”的轻量化定位，还会面临 Windows 嵌套作业对象的兼容性风险。
- **强烈赞同 Claude 的「看门程序（`bin/acp-guard.mjs`）+ 启动清理兜底」架构**：
  - **看门程序作为主手段**：通过 stdio 管道透传和定时心跳（`process.kill(daemonPid, 0)`），在守护进程遭遇崩溃、硬杀或终端关闭导致 stdin EOF 时，看门程序能在秒级内感知并自动执行 `taskkill /T /F` 清理目标代理树，真正做到即死即消，无需等到下次桥启动。
  - **启动清理作为兜底**：记录 PID 与进程创建时间（如 PowerShell `Get-Process`），只有两者完全匹配才予以清理，彻底避免 Windows PID 复用导致的误杀。
  - 此组合兼顾了实时性与安全性，且为 100% 纯 Node.js 实现。

### 3. 议题 ④：退避档位规范与实现统一（2 档 vs 3 档）
- **反对 Claude 提议的“改为 3 档（30s、2m、10m，第 4 次才停止）”**；
- **坚定支持 DeepSeek、Codex 及我方主张的“维持 2 档（30s、120s），第 3 次失败即停止人工介入”**：
  - **原因 1：快速失败原则**。如果一个后台代理连续崩溃 3 次，99% 的概率是硬性故障（如路径配置错误、权限不可访问、环境损坏或 Key 失效）。此时让系统盲目挂起 10 分钟毫无价值，反而会让用户误以为还在正常执行，尽早停止并报告错误才是正确的交互体验。
  - **原因 2：全局门铃已有 10 分钟冷却兜底**。`doorbells.cooldown_seconds`（默认 600 秒）本身就负责唤醒降级。

# 互评：deepseek

先给结论：四方在“取消超时不应算进程失败”“孤儿清理必须有启动兜底”“allow 风险要写清楚”“notes 要进定稿信”上一致；真正的分歧是 ① 宽限怎么配、② 防孤儿用 Job Object 还是监督进程、④ 退避两档还是三档、⑤ notes 的范围。下面逐条，并收回我上一轮的几处过度设计。

## ① 取消宽限

**同意**
- claude、codex 和我都认为：取消超时不能走 `fail()` 的失败计数和退避。3 秒误杀一次“停止 run”是当前最直接的问题。
- codex 指出的租约竞态很关键：`stopRun()` 会立刻 `releaseLeasesOfRun`，宽限拉到 20–30 秒后，旧 ACP 回合可能还在写，新任务却已拿到同一 paths。这是延长宽限**新引入**的风险，必须和宽限同批处理，否则修一个 bug 引入另一个。
- antigravity、claude 都提到 `doctor --probe` 也要走同一生命周期，避免探针留下进程。

**不同意／修正**
- 15 秒（antigravity）偏短：Antigravity 一个回合 40 秒以上，取消时若正卡在工具调用，15 秒仍可能误杀。20 秒（codex）可接受，但我仍建议默认 30 秒，并且**记录每次取消的实际耗时**，让用户按产品调 env，而不是先猜一个偏小的值。
- 我上轮的“收到 `session/update` 就按 10 秒续期到 120 秒”**放弃**：它把回合生命周期拉长，和租约保护叠加后复杂度不划算。固定 env 宽限 + 超时杀进程已能覆盖；真需要更久的产品自己调 env。claude/antigravity/codex 都没提续期，接受多数意见。
- 我上轮“连续 3 次取消超时就 stopped”也**放弃**：连续强杀重启本身能自愈；接进 3 次停机会让正常停止 run 有停掉成员的风险。保留事件与面板提示即可。
- 配置方式：我上轮想加 `acp.cancel_grace_seconds`/`retry_seconds` 到 `config.ts`，这和 notes 争同一个文件，逼着 T1→T3 串行。接受 claude/antigravity/codex 的 env 方案（沿用 `BRIDGE_ACP_CANCEL_GRACE_SECONDS`、`BRIDGE_ACP_RETRY_SECONDS`），把“可调”写进 USAGE；以后确有按成员差异化的需求再加配置。这样 T1/T3 可以并行。
- 租约保护的具体做法建议 v1 取最小面：`stopRun()` 时若存在正在取消的 ACP 回合，**延迟释放该 run 的租约**，或让 scheduler 在取消完成前不启动 paths 有重叠的任务。验收必须有一条：旧 run 取消未确认时，新 run 不能拿到同一 paths。
- codex 的“主动取消保留当前计数”：可以理解为取消不清零失败计数，但**取消超时本身不能 +1**，别把“保留”做成“累计”。

## ② 孤儿进程

**同意**
- 启动清理是必须项，不是可选项。用现有 `agent_endpoints`（kind `acp-pid`）比我上轮新建 `.bridge/acp-hosts.json` 好：持久化、已有读写接口；记录真实代理 PID + 创建时间（最好再加命令行/项目归属校验），下次启动只清理对得上的条目。
- claude 的 guard 和我的 supervisor 是同一思路：stdio 透传 + 父进程死亡时清理；codex/antigravity 的 Job Object 在“代理再派生的后代”上确实更强。
- 必须测：代理自己再 spawn 子进程、守护进程被任务管理器结束、代理先自己退出、正常 stop、无关同名进程不被误杀、`doctor --probe` 不留进程。

**不同意／修正**
- Job Object 的可行性：项目目前没有 native 依赖，Node 也没有 Job API。codex 说的“辅助进程监视守护进程真实句柄”落地后，其实就是一个 Job 加持的 guard：辅助进程要拿句柄、建 Job、转发 stdio、在父进程退出时关 Job。它比纯 Node guard 多一层 Win32 复杂度，收益是 detached/breakaway 的后代也一起死。建议**不要把它设为主线**，而是作为 T2 里的限时验证：能证明纯 Node、可打包、当前宿主可用就采用，否则退回 supervisor + `taskkill /T` + 启动清理。任务验收按结果写：强杀守护进程后代理及其后代都不在，不绑定实现。
- claude 的 guard 每 2 秒 `process.kill(daemonPid, 0)` 轮询：PID 可能被复用，单靠它会在极端情况下误判；stdin EOF 才是权威信号（守护进程死亡时管道必然关闭），轮询只能当兜底，且建议比对守护进程启动时间。建议**以 EOF 为主**。

- codex 的“代理开始执行之前建立归属”很关键；若最终走 guard，也要 spawn 后立即写记录，别等 initialize 成功。

### ① 取消宽限

赞成 Claude 用环境变量调宽限，也赞成 Claude 和 DeepSeek 将取消超时与进程故障分开。我把上一轮的 20 秒和「超时计一次故障」改为 **默认 30 秒、可配置的固定期限**。Antigravity 提的 15 秒可以用作配置值，选默认值时应测从发送 `session/cancel` 到原 prompt 返回的时间，完整回合的时长只能作为线索。DeepSeek 建议按 `session/update` 续期到 120 秒，但取消后仍可收到增量输出，只有原 prompt 结束或进程树退出才能解除对后续工作的阻塞。

### ② Windows 进程回收

接受 Claude 和 DeepSeek 的纯 Node 监督进程作为第一条验证路线，避免把原生构建引入发布流程。以父进程专用管道 EOF 或 IPC 断开触发清理，并实测强杀场景。`process.kill(pid, 0)` 只能探测存在性。Antigravity 的进程名或命令特征核对、DeepSeek 的 5 秒时间容差都不足以授权结束进程。

我上一轮优先选 Job Object，现在建议用验收决定：只强杀临时 daemon 后验证代理和后代均退出，再验证代理根进程先退出、后代仍活着的情况。只对已退出的根 PID 调 `taskkill /T` 无法提供这项保证。监督方案达不到整树验收就采用独立 Job Object。若加启动兜底，应在端口成功绑定后、首次 ACP 投递前执行，核实原守护进程已退出、项目归属及待回收进程的精确创建时间。监督进程已死亡时应独立校验存活的代理项。测试脚本已有子进程 PID，省去新增 `/api/health`。 [Node.js 进程存在性检查](https://nodejs.org/api/process.html#processkillpid-signal) · [Windows 进程句柄与 PID](https://learn.microsoft.com/en-us/windows/win32/procthread/process-handles-and-identifiers) · [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

### ③ 权限说明

赞成三方补 USAGE，并沿用 `deny` 示例。Claude 的 shell 实测适合作例子。Antigravity 的「授予完全宿主权限」表述过宽，应该写成桥自动批准代理提交的 ACP 权限请求，可能涉及 shell 和项目外文件，实际能力仍受代理配置和账号权限约束。`allow_once` 缺失时可能选 `allow_always`，由代理决定记忆范围。DeepSeek 提到的逐次人工确认应走支持确认的前台模式，后台 `deny` 是自动拒绝策略。 [ACP 权限选项](https://agentclientprotocol.com/protocol/v1/tool-calls#permission-options)

### ④ 退避

  - 超时记一条 `acp_cancel_timeout` 事件，结束进程树，把已取走但没确认的信退回；
  - 不增加失败次数，不进入退避，也不会因为取消超时而停止成员；
  - 原来累计的失败次数保持不变，不清零。
  - 有有效的未读信时，懒启动并恢复原会话。
- **记录耗时**：每次取消都记下从发出 `session/cancel` 到回合结束的实际耗时，方便以后调整默认值。
- **租约保护（随宽限一起交付）**：停止 run 或任务被替换时，如果这个任务的 ACP 回合还没结束，就推迟释放它的租约，直到回合结束或进程树退出。
  - 在此期间，调度器不启动路径重叠的任务。
  - 没有 paths 的流水线任务，等到旧回合结束才启动。
  - 最长等待等于宽限时间，再加上结束进程的时间。

### ② Windows 孤儿进程
- **主手段**：新建一个 Node 监督进程 `bin/acp-supervisor.mjs`。
  - 后台代理和 `doctor --probe` 探针都经它启动。它负责转发代理的输入和输出，不改报文内容。
  - 它把来自守护进程的管道当作生命线：守护进程一死，管道立即断开（EOF），监督进程随即对代理执行 `taskkill /T /F`，然后自己退出。
  - 用 `process.kill(pid, 0)` 轮询守护进程只作辅助手段，不能作为结束进程的依据。
- **启动清理（兜底）**：
  - 台账放在 `<项目>/.bridge/acp-hosts.json`，由进程层模块读写，不经过 `acp.ts`，这样 T2 和 T1 可以并行。
  - spawn 后立即写一条记录，内容包括：监督进程和代理的 PID、各自精确的创建时间、项目目录、守护进程 PID 及其创建时间。
  - 守护进程在端口绑定成功后、第一次投递 ACP 之前做清理。只清理同时满足三个条件的进程：
    1. 原守护进程已经退出；
    2. 属于本项目；
    3. PID 和精确创建时间都对得上，监督进程还要核对命令行里有 `acp-supervisor.mjs`。
  - 不符合条件的记录只记事件，不动进程。
- **Job Object 不在这一轮做**。
  - 验收要求：只强制结束临时守护进程后，代理及其子进程都退出。
  - 「根进程先退出、它派生的子进程还活着」这种情况，要写测试，并如实记录结果。如果监督进程覆盖不到，就记为已知限制，以后单独评估 Job Object。

### 关键决策

- 取消宽限默认 30 秒，用环境变量调整，不加配置项，不动态续期 —— Antigravity 一个回合 40 秒以上，15 秒和 20 秒都容易误杀。用环境变量可以避开 config.ts 的写入冲突，让任务并行；续期和租约保护叠在一起，行为难以预测。
- 取消超时不计失败、不退避、不停止成员，已有的失败次数保持不变 —— 代理没理会取消不等于坏了。若计入失败，用户正常停两次 run 就会触发退避；若把次数清零，又会掩盖真实的故障。
- 延长宽限的同时，租约保留到旧 ACP 回合结束，覆盖没有 paths 的流水线 —— stopRun 会立刻释放租约。宽限变长后，旧回合还在写文件时，新任务就可能改同一批文件。只修宽限、不加保护，等于修一个问题又引入一个新问题。
- 孤儿进程用 Node 监督进程（管道断开即清理），再加台账和启动清理；Job Object 这一轮不做 —— 守护进程一死管道就会断开，这是最可靠的信号。Node 没有 Job Object API，用它要引入原生模块或 C# 辅助进程，会破坏免编译安装。「根进程先退出」的情况用测试如实记录，留给以后评估。

- 退避保持 30 秒、2 分钟两档，第 3 次失败停止；改的是 M3 需求文档那句话，代码不改 —— 需求原句自相矛盾，三档退避和「3 次失败停止」不能同时成立。两档是已发布的行为，快速失败让人更早介入。四位成员里有三位主张这样做。

### T1 ACP 取消宽限与取消期间的租约保护

【宽限】默认 30 秒，可用 BRIDGE_ACP_CANCEL_GRACE_SECONDS 覆盖；是固定期限，不随代理输出续期。
【按时结束】宽限内收到原 prompt 返回的 cancelled，就正常结束回合，会话保留。
【超时】记 acp_cancel_timeout，结束进程树，把取走但未确认的信退回。不增加失败次数，不进入退避，不停止成员；原有失败次数保持不变。有有效未读信时，懒启动并恢复原会话。
【记录】每次取消记下从发出 cancel 到回合结束的耗时。
【租约保护】停止 run 或任务被替换时，如果该任务的 ACP 回合还没结束，就推迟释放它的租约，直到回合结束或进程树退出。期间调度器不启动路径重叠的任务；没有 paths 的流水线任务等旧回合结束再启动。
【退避】保持 30 秒、2 分钟、第 3 次失败停止。同一次故障只启动一个退避计时器。
【验收】在 scripts/acp-smoke.ts 里覆盖以下情况，假代理可用环境变量控制「延迟确认取消」和「忽略取消」：
(a) 确认时间超过旧的 3 秒、但在宽限内：正常结束，进程不被结束；
(b) 忽略取消：超时后结束进程，失败次数不变，不进入 retrying；下一封信 resume 原会话；
(c) 旧 run 还在取消期间，新 run 里路径重叠的任务没有开始，旧回合结束后才开始；
(d) 取消期间来的有效信会补发，同一会话没有重叠的回合；
(e) 连续 3 次进程故障后停止，手动重启后恢复。
